# What actually broke, running this for real

## Why this file exists

Every other file in this folder explains how the finished system works. This one is different on purpose: it's the honest, chronological record of everything that went wrong between "the code compiles" and "the code actually works against live APIs," because that gap is where the real learning happened, and it would be dishonest to pretend the first version just worked.

## The seven things, in the order they actually happened

**A model had quietly retired.** The default model shipped in this project, `gemini-2.5-flash`, turned out to be retiring October 16, 2026, confirmed directly against Google's own deprecation schedule rather than assumed. The fix was a one-line default change. The lesson wasn't about Gemini specifically, it was a direct repeat of something this project's wider curriculum already learned the hard way: a model name that worked last month is not guaranteed to work today, and checking a provider's current documentation beats trusting a default that was correct when it was written.

**Reasoning models can silently eat their own answer.** This happened twice, once on each provider, which is the part worth remembering more than either individual fix. Gemini's `classify` call asked for a one-word answer with `max_tokens=10`. Gemini 3.5 is a reasoning model, and its internal thinking tokens share the exact same budget as the visible answer. The model spent all 10 tokens thinking and returned nothing. The identical shape of bug then showed up on Groq's side: the billing loop returned `order_id: None` on every single attempt, not because the model guessed wrong three different ways, but because it never produced a parseable answer at all. Both were fixed the same way: reduce or disable the reasoning overhead for simple tasks, and treat the token budget as something a reasoning model's internal process competes for, not something only the visible answer uses.

**A check that was correct and still let a bad answer through.** Against a real $49.99 order, a proposed $0.01 refund passed every rule that existed: positive number, under the policy cap, not more than the order's value. Every individual check was doing its job. Together, they left room for an answer that was technically legal and completely wrong. The fix added one more condition, that the amount has to be within 90% of the order's real value, closing the gap between "passes every stated rule" and "is actually a sensible answer."

**Rate limits and server errors are not the same failure, and don't deserve the same response.** A `503` is usually a brief server hiccup, worth a short retry. A `429` means a quota is genuinely exhausted for a window of time, and retrying quickly just wastes attempts inside the same exhausted window. The original code used identical short backoffs for both. The fix gave 429s a much longer, separate backoff schedule, and also made sure one ticket exhausting its retries didn't take the other two down with it.

**A real secret ended up in plain text.** Gemini's API puts the key directly in the request URL. An unhandled error naturally prints that whole URL. This isn't a hypothetical risk, it happened, visibly, in real terminal output during testing. The fix redacts the key from every error message before it can reach a print statement or a traceback, confirmed with a test asserting the raw key can never appear in what gets shown.

**The most important one: a check leaking its own answer key.** The ticket text never states a dollar amount ("I never received my order" has no price in it), yet the model was being asked to propose a refund amount anyway. When its guess was wrong, the rejection message said exactly what the correct amount was. The next attempt didn't need to reason about anything, it just had to notice the number already sitting in its own feedback. The real fix wasn't a smarter prompt, it was recognizing the model should never have been asked to guess a fact that already existed in a real record. The amount is now looked up directly, the model's only job is identifying which order, a task the ticket text actually supports.

## The one pattern underneath all seven

None of these were caught by reading the code and reasoning about whether it looked right. Every single one was caught by actually running it against a real API, reading the real output, and noticing when a result didn't match what the code claimed it should do. "It compiles" and "the logic reads correctly" were never once sufficient on their own, across any of these seven, to mean the code actually worked.
